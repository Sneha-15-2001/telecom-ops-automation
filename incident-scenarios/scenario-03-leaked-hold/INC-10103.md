# INC-10103 — Leaked reservation blocks an MSISDN

- **Status:** Open (P3)
- **Reported:** inventory ops — "numbers showing reserved for a dead order, pool shrinking"
- **Symptom:** resource stuck `RESERVED` against order 9999 (which never completes);
  reservation `ACTIVE` with a 1-minute TTL nobody honored.
- **Suspected area:** fulfillment crashed between reserve and confirm, no expiry sweeper ran.

## 🧑‍💼 What the reporter says

Last week a test order (9999, since cancelled) reserved a prime MSISDN with a
1-minute TTL. The fulfillment process died right after reserving — before
confirm or release — and there is no background sweeper that expires stale
holds. The reservation stayed `ACTIVE` forever and the number stayed
`RESERVED`, silently shrinking the sellable pool. Nobody noticed until the
pool monitor flagged falling availability.

## 🔧 Engineering notes

### Timeline recovered from the system

1. `RESOURCE_RESERVED` — MSISDN held for order 9999 (see resource history)
2. `expiresAt` passed with no confirm/cancel
3. **Silence** — no `RESOURCE_ALLOCATED`, no `RESOURCE_RELEASED`; the hold leaks

### How to reproduce

```bash
bash incident-scenarios/scenario-03-leaked-hold/setup.sh
```

### Evidence to collect

- `GET /api/inventory/resources/{id}` → `RESERVED`, `orderId=9999`
- `GET /api/inventory/reservations/{id}` → `ACTIVE`, `expiresAt` in the past, no confirm/cancel
- `GET /api/inventory/resources/{id}/history` → `RESOURCE_RESERVED` with no follow-up event
- Logs: `RESOURCE_RESERVED` with no matching `RESOURCE_ALLOCATED`/`RESOURCE_RELEASED`.
