# INC-10117 — HTTP 501 Not Implemented: integration calling capabilities that do not exist

- **Status:** Open (P2)
- **Reported:** a partner integration
- **Symptom:** 501 `NOT_IMPLEMENTED` on payment capture, network activation and refund.
- **Suspected area:** none — this is the system correctly refusing work it cannot do.

## 🧑‍💼 What the reporter says

Our integration team wired up payment capture, activation and refund against
your sandbox. All three return 501. We cannot tell whether these are
permanently unavailable or misconfigured on our side.

## 🔧 Engineering notes

### This one is working as designed

501 means the endpoint is understood and the method is valid, but this
deployment cannot support the capability. That is the honest answer here: no
payment gateway is integrated and provisioning never contacts an HLR.

The alternatives would both be worse:

- **404** would imply the URL is wrong, sending the partner hunting for a typo.
- **200 with a fake success** would let them build against a system that does not
  actually move money or touch the network — and would only fail in production.

Each 501 body names what must be integrated first:

| Endpoint | Blocked on |
|---|---|
| `POST /api/unimplemented/orders/{id}/payment-capture` | A PSP (Razorpay, Stripe) |
| `POST /api/unimplemented/orders/{id}/network-activation` | Mediation + HLR/HSS/OSS adapter |
| `POST /api/unimplemented/orders/{id}/refund` | Refund support in the payment gateway |

### How to reproduce

```bash
bash incident-scenarios/scenario-17-not-implemented-501/setup.sh
```

No fault injection needed — the 501 is permanent until the capability is built.

### Resolution

This is a documentation and roadmap ticket, not a defect. Answer the partner with
the three integration requirements above.
