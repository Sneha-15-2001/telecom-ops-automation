# INC-10115 — HTTP 502 Bad Gateway: order validation cannot reach customer-service

- **Status:** Open (P1)
- **Reported:** storefront — "we're getting bad gateway, orders won't validate"
- **Symptom:** `POST /api/orders/{id}/validate` returns **502** with `UPSTREAM_ERROR`.
- **Suspected area:** order-service → customer-service call during validation.

## 🧑‍💼 What the reporter says

Since roughly 09:10 the storefront has been throwing up a 502 whenever an agent
tries to validate an order. The channel is telling customers "service
temporarily unavailable". Support says nothing is wrong with the orders
themselves — the same customers placed orders fine an hour ago.

## 🔧 Engineering notes

### What 502 means here

502 is *not* an order-service failure. order-service is up and answering. The
fault is with the service behind it: customer-service returned a 5xx, so
order-service could not obtain a valid answer and passed the failure up. A
client seeing 502 should **not** retry blindly into a different order — the
order is untouched.

### Timeline recovered from the system

1. `ORDER_CREATED` — order accepted normally
2. `STATUS_CHANGED CREATED → VALIDATING` — validation started
3. `CUSTOMER_VALIDATE_CALL customerId=1 outcome=UPSTREAM_ERROR status=500`
4. `BAD_GATEWAY dependency=customer-service upstreamStatus=500`
5. Transaction rolls back — **the order is still `CREATED`**

### The important property

Check `GET /api/orders/{id}/status`. It must read `CREATED`, **not** `FAILED`.
An earlier version converted an unreachable CRM into `valid=false`, which
permanently failed customer orders because of someone else's outage. A
transient infrastructure failure must leave the order retryable.

### How to reproduce

```bash
bash incident-scenarios/scenario-15-upstream-502/setup.sh
curl -X POST http://localhost:8082/api/orders/{id}/validate   # 502
curl http://localhost:8082/api/orders/{id}/status             # CREATED
curl -X DELETE "http://localhost:8081/api/chaos/fault?path=*" # recover
```

Requires `CHAOS_ENABLED=true` on customer-service.

### Likely fix

customer-service is the thing actually returning 500. Find its stack trace via
the correlation ID in the 502 body, fix that, and the 502s stop on their own.
No change to order-service is needed — it is already behaving correctly.
