# INC-10120 — HTTP 409 Conflict: concurrent lifecycle actions on one order

- **Status:** Open (P3)
- **Reported:** support
- **Symptom:** one of two simultaneous submits fails with 409.
- **Suspected area:** none — this is correct behaviour being misread as an error.

## 🧑‍💼 What the reporter says

"An order failed with a conflict error and nobody knows why. The order looks
fine and the customer says it was submitted twice."

## 🔧 Engineering notes

### 409 is the right answer

Two agents (or an agent and an automation) acted on the same order. One
submitted it; the order is now `PAYMENT_PENDING`; the other tried to submit it
again, and `submit` is only legal from `VALIDATED`. The loser gets
`409 ORDER_STATE_INVALID`.

This was previously a **400**, which was actively misleading: 400 tells a client
"change your payload", so an integration would retry with the same payload
forever. 409 tells it "re-read the resource and decide what to do next" — which
for this case means "someone else already submitted it; carry on".

### Read-only note

There is a related weakness: `CustomerOrder` has no `@Version`, so two truly
simultaneous writes are last-write-wins rather than rejected. The check-then-act
window here is narrow but real. Adding optimistic locking would close it.

### How to reproduce

```bash
bash incident-scenarios/scenario-20-conflict-409/setup.sh
```

Exactly one submit returns 200 and one returns 409. If **both** return 200 the
order was submitted twice — that is the real bug.

### Resolution

Not a defect. Improve the client to treat 409 on a lifecycle endpoint as
"already done", not as a failure to retry.
