# INC-10118 — HTTP 429 Too Many Requests: order intake throttled

- **Status:** Open (P2)
- **Reported:** channel team
- **Symptom:** `429` with `RATE_LIMIT_EXCEEDED`; agents see "too many requests".
- **Suspected area:** order intake exceeding its budget.

## 🧑‍💼 What the reporter says

Half the agents in one branch are getting errors when they try to save orders.
Their first thought is that the system is broken. The other half are working
fine, which makes it look random.

## 🔧 Engineering notes

### Not random — it is per-client

The limiter is a fixed window keyed on client address (`X-Forwarded-For` when
present). Agents behind one NAT share a budget, so a busy branch starves itself
while another branch is unaffected. That asymmetry is exactly the symptom
described.

Budget: **120 requests / 60 seconds** per client.

### Headers a client needs

```
Retry-After: 49
X-RateLimit-Limit: 120
X-RateLimit-Remaining: 0
```

A well-behaved client backs off for `Retry-After` seconds. An agent clicking
"save" repeatedly makes it worse — each retry spends budget.

### Health checks are exempt

`/actuator`, `/v3/api-docs` and `/swagger-ui` bypass the limiter. A monitoring
probe that got 429 would report the service as down when it is healthy.

### Known limitation

The counter is in-memory and per instance. Behind a load balancer each instance
enforces its own budget, so the effective limit is `limit × instances`. A real
deployment needs a shared counter (Redis) or a gateway-level limit.

### How to reproduce

```bash
bash incident-scenarios/scenario-18-rate-limited-429/setup.sh
```

**Wait ~60s afterwards** for the window to reset, or the next order scenario will
be throttled too.
