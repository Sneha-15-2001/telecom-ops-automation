# INC-10116 — HTTP 503 Service Unavailable: order intake refusing

- **Status:** Open (P1)
- **Reported:** channel monitoring
- **Symptom:** all order endpoints return **503** with `SERVICE_UNAVAILABLE`.
- **Suspected area:** order-service refusing traffic — drained pool, open circuit breaker, or a dependency-down guard.

## 🧑‍💼 What the reporter says

Every order call has started returning 503. The health endpoint still says UP,
which is confusing — monitoring is green while the business is fully down.

## 🔧 Engineering notes

### 503 vs 502 — do not mix them up

| | Meaning | Caller action |
|---|---|---|
| **502** | A dependency answered, unusably | Fix the dependency; the request was never applied |
| **503** | *This* service (or a guard in front of it) is refusing | Back off, retry with `Retry-After` |

Both are transient. Neither should ever mark a customer order `FAILED`.

### Why health says UP

`/actuator/health` reports the JVM and the database. It does not know the
service is refusing business traffic — a dependency guard can 503 every request
while the process itself is perfectly healthy. This gap is real: health should
include a readiness check that fails when dependencies are down.

### How to reproduce

```bash
bash incident-scenarios/scenario-16-dependency-503/setup.sh
curl -X DELETE "http://localhost:8082/api/chaos/fault?path=*"
```

### Likely fix

Order-service is refusing deliberately. Find why — a circuit breaker open on a
flapping dependency, an exhausted connection pool, or the dependency-down guard
firing. Then fix that, not the 503.
