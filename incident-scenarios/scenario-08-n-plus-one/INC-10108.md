# INC-10108 — Order list slow: N+1 selects on order items

- **Status:** Open (P2)
- **Reported:** storefront team — "order queue page takes seconds with 50+ orders"
- **Symptom:** one `GET /api/orders?page=0&size=15` fires ~15 extra
  `select … from order_item where order_id=?` queries — one per order.
- **Suspected area:** `OrderMapper.toResponse` calls
  `items.findByOrderIdOrderByIdAsc` inside the page mapping (no fetch join /
  entity graph / batch size). Same shape exists in timeline assembly.

## 🧑‍💼 What the reporter says

As order volume grew past a few hundred rows, the ops queue page degraded
linearly: 15 rows → ~16 queries, 50 rows → ~51. Nobody noticed in dev with 3
rows. The database CPU graph climbed every morning when the back office opened
the queue. It is a performance incident, not a correctness one — responses are
right, just slow, and it will topple the page at scale.

## 🔧 Engineering notes

### Timeline recovered from the system

1. Orders accumulated over weeks (bulk imports + storefront)
2. Each list call: 1 page query + N item queries (see SQL log evidence)
3. p95 of `GET /api/orders` grows with table size; DB CPU follows

### How to reproduce

```bash
bash incident-scenarios/scenario-08-n-plus-one/setup.sh
# prints the per-page item-select count (expect ≈ page size)
```

### Evidence to collect

- `order_item` select count jumps by ~page-size per list call (script prints it)
- SQL log shows identical `where order_id=?` binds, one per order id
- No error anywhere — pure latency, visible in response times

## Investigator input (Phase 14)

`GET /api/orders is slow: N+1 selects on order_item, one per order in the page.`

## Fix direction (Phase 17, NOT implemented here)

Fetch join / `@EntityGraph` / `@BatchSize` on `CustomerOrder.items`, or a
single `findByOrderIdIn(ids)` + in-memory grouping. Deliberately left broken
so the AI code-fix recommender has a real target.
