# INC-10121 — HTTP 502 during fulfillment: inventory-service failing mid-saga

- **Status:** Open (P1)
- **Reported:** provisioning operations
- **Symptom:** `POST /api/orders/{id}/fulfill` returns **502**; `UPSTREAM_ERROR`.
- **Suspected area:** order-service → inventory-service during the fulfillment saga.

## 🧑‍💼 What the reporter says

"Orders are failing at activation with a bad-gateway error. We have paid for
them. The number pool looks normal when we look at the inventory screen."

## 🔧 Engineering notes

### The saga took a hold it could not use

Fulfillment is reserve → provision → notify. inventory-service errored on the
stock lookup, so the saga aborted. The check that matters is what it left
behind:

```
GET /api/inventory/reservations/order/{orderId}   →  must be empty
```

An older version swallowed the inventory exception and reported
`INVENTORY_SHORTAGE`, which reads as "we ran out of numbers" and sends operators
to the stockroom during a platform outage. The client now reports 502 and names
inventory-service as the fault.

### Secondary risk: silent partial compensation

Compensation is best-effort. If the release call itself fails, the order still
reports cancelled while the number stays held. There is no retry and no
reconciliation job — the leak only surfaces later as a shrinking pool. Worth an
outbox and a sweeper.

### How to reproduce

```bash
bash incident-scenarios/scenario-21-cascade-502/setup.sh
curl http://localhost:8083/api/inventory/reservations/order/{orderId}
curl -X DELETE "http://localhost:8083/api/chaos/fault?path=*"
```

### Likely fix

inventory-service is returning 500. Find its stack trace via the correlation ID.
Then check for held resources from the window — any leak there is recoverable by
releasing the reservation.
