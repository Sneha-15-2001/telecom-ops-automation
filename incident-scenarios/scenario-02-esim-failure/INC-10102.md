# INC-10102 — eSIM provisioning FAILED (MISSING_MSISDN)

- **Status:** Open (P2)
- **Reported:** activation team — "eSIM orders keep failing at 2 AM batch"
- **Symptom:** provisioning request ends `FAILED`, `lastError` = `MISSING_MSISDN`.
- **Suspected area:** order item carried no MSISDN and no eSIM profile was reserved.

## 🧑‍💼 What the reporter says

During last night's eSIM batch, the order management screen created a
provisioning request straight from the order item — but the item had no MSISDN
(the number reservation step was skipped for eSIM orders in the old flow).
`start` succeeded because it performs no checks; `activate` then ran the
deterministic rule "ESIM requires an MSISDN" and failed the request. Ops
re-tried the batch twice against the same request, burning attempts, before
escalating. The eSIM profile was never delivered.

## 🔧 Engineering notes

### Timeline recovered from the system

1. `PROVISIONING_CREATED` — ESIM request opened, `msisdn: null`
2. `STATUS_CHANGED PENDING → IN_PROGRESS` — start (no validation here)
3. `STATUS_CHANGED IN_PROGRESS → FAILED` — `MISSING_MSISDN`
4. No retry/reprocess followed; request left FAILED

### How to reproduce

```bash
bash incident-scenarios/scenario-02-esim-failure/setup.sh
```

### Evidence to collect

- `GET /api/provisioning/{id}` → `FAILED`, `lastError` contains `MISSING_MSISDN`
- `GET /api/provisioning/{id}/history` → `STATUS_CHANGED IN_PROGRESS → FAILED`
- Logs: `PROVISIONING_FAILED` with the same correlation ID; no `RESOURCE_RESERVED`
  for the order — fulfillment skipped reservation or the item had no number.
